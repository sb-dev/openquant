# Cross-runtime protocol fixtures

Status: S0 and S1 fixtures implemented. Rust validates every fixture, and the TypeScript contract layer gives every entry the same verdict, code and digest (`packages/api-contracts/ts`). No API or worker uses the S1 envelopes yet.

## Manifest

`manifest.json` lists every payload with its contract, expectation (`valid`, `schema_invalid` or `semantic_invalid`) and failure code. Paths in the manifest are relative to `fixtures`. A test fails if a file is missing from the manifest. `with_strategy` and `with_input` name the payload that a semantic check reads beside the fixture.

## S0 payloads

S0 adds valid/invalid strategy/evaluation input, numerical result and checkpoint payloads against the schemas in `packages/api-contracts/schemas`. Rust validates them and verifies serialized state restore. The valid result and checkpoint payloads were emitted once from the F0 smoke case as schema examples; they are not numerical goldens. Include unsupported versions, unknown mandatory fields, decimal precision, invalid operator IDs/types/units, malformed identities and mismatched checkpoint identities. The `exact-*` payloads cover the `Exact` checkpoint value: valid fractions from a real run, and invalid forms (not reduced, denominator 1, decimal-representable, zero denominator, beyond 128 bits, a fraction in a money or result field).

## S1 envelopes

S1 adds fixtures for the connected envelopes in `packages/api-contracts/schemas` ([architecture §7](../../docs/specs/05-system-architecture-and-data-spec.md#7-data-and-protocol-contracts)). They cover the evaluation plan, request and submission; job dispatch and attempt claim; commands; the research profile, cohort policy and dataset manifest; retrieval requests and results; validation results, metrics and gate reports; agent dispatch and attempt results; API errors; and the release manifest.

- `valid/` holds valid payloads. `input.provider-source` is an engine-scope evaluation input: the synthetic F0 bars with the provider source value, which changes no result.
- `invalid/` holds `schema_invalid` payloads: unsupported versions, unknown fields, malformed digests and decimals, and combinations that an envelope forbids.
- The S1 entries are appended to the manifest. The S0 entries and their files are unchanged.
- A fixture that cites another fixture cites its canonical SHA-256 digest. When a cited fixture changes, recompute its digest and update every fixture that cites it.
- Provider-shaped payloads, such as dataset manifests and job dispatches, use an obviously synthetic instrument and round synthetic values. They hold no real market data ([publication and data policy](../../docs/specs/07-open-source-project-organisation-spec.md#7-publication-and-data-policy)).
- A case whose verdict depends on attempt ownership, such as stale ownership or a late completion, needs the API's state. It arrives with the API as a `semantic_invalid` entry that declares its attempt context.
- `api-error.value-bound-*` payloads hold more values than the TypeScript value bound of `api-error/1`, which is 4,096, the structural value limit, except `-wrong-version-at-4096`, which holds exactly 4,096. They pin the order of the checks past that bound in both runtimes: a strict-JSON error anywhere, then the version tag, then the bound. `-wrong-version-at-4096` puts the version tag at value 4,096, the last value inside the bound, and the `-at-4097` payloads put it at value 4,097, the first value past the bound, so the tag is read also when it is the value that passes the bound. The payloads of 20,000 values and more, including `-at-20000` and `-at-20001`, were written when the limit was 20,000; they now lie past the bound and pin the same order there. They are written on one line.
- `dataset-manifest.listed-decimals-at-4096` and `dataset-manifest.unlisted-decimals-at-4097` pin the structural value limit, under which an invalid document's violations are listed. Their only violations are three decimal-grammar failures. With 4,096 values they are listed, so the code is `INVALID_DECIMAL`; with one more value the listing stops at the first violation, so it is `SCHEMA_VIOLATION`, in both runtimes.
- `evaluation-input.listed-decimals-at-4096` and `evaluation-input.unlisted-decimals-at-4097` pin the same limit on an engine input: the F0 input with 400 bars, three decimal-grammar failures in its first bar, and copies of a session and of an unplanned event that bring it to 4,096 or 4,097 values. S1 P1 lowered the limit from 20,000, so an invalid engine input of 4,097 to 20,000 values with only decimal-grammar failures now reports `SCHEMA_VIOLATION`.
- `api-error.long-key-*` payloads hold an object key whose text is longer than the TypeScript key limit of 256 bytes: at the top level (an escape, ASCII and a character outside Latin-1, 300 bytes), nested in a violation (257 bytes), before another version tag (`UNSUPPORTED_SCHEMA_VERSION`), and repeated before another version tag, the second time with escapes (a duplicate key, `SCHEMA_VIOLATION`). TypeScript never decodes such a key; Rust reaches its schema with it and rejects it with the same code. `cohort-policy.escaped-longest-keys` is the pilot policy with `schema_version` and its three longest property names, of 25 bytes, written with every character escaped: 150 bytes of text, within the limit, and valid in both runtimes.
- `api-error.maximal-listing` is the largest listing that `api-error/1` carries: 21 violations (20 and the entry with an empty pointer that counts the rest), the first with a pointer of 1,024 characters and a message of 1,000, the schema maxima. It is a boundary of the schema, not a pointer that the contract layer could produce. `api-error.violations-22` and `api-error.pointer-1025` are one entry and one character more, both `SCHEMA_VIOLATION`.
- `command.create-mission-amount-leading-zero`, `agent-attempt-result.cost-amount-exponent` and `cohort-policy.cost-stress-multiplier-negative-leading-zero` pin `SCHEMA_VIOLATION` for a malformed amount inside a failing `oneOf` (`command/1`, the cost usage of `agent-attempt-result/1`) and for a malformed `StressMultiplier` that starts with `-` and so also fails the sign rule of its type. A malformed decimal with no `oneOf` above it and no sign rule, such as `agent-dispatch.cost-reservation-exponent` and `cohort-policy.cost-stress-multiplier-exponent`, is `INVALID_DECIMAL` (OQ-05 section 7).
- `validation-result.*` payloads cover the two forms: a seed has no parent and no change scope, and a valid revision has the scope `ENTRY` or `EXIT`. `revision-scope` is a revision that changes both rules, recorded as `INVALID` with `REVISION_SCOPE`.
- `retrieval-result.*-retryable` payloads mark retryable a failure class that is never retried, including `EGRESS_REFUSED`.
- `api-error.wrong-version-duplicate-key` and `-float` pin that strict JSON runs before the version check: they are `SCHEMA_VIOLATION`, not `UNSUPPORTED_SCHEMA_VERSION`. `api-error.wrong-version-unsafe-integer` pins the other order for the unsafe-integer rule, which is not a strict-JSON error: the version check runs first and the code is `UNSUPPORTED_SCHEMA_VERSION` (OQ-05 section 7).
- Bytes that are not UTF-8 are not committed, because the repository checks read every tracked file as text. The Rust contracts-report test and the TypeScript validation test build the same byte strings and both expect `SCHEMA_VIOLATION`.

The TypeScript layer runs every shared payload and compares its verdict, code and, for a valid payload, digest with Rust (`packages/api-contracts/ts/test/parity.test.ts`). Keep provisional harness-only wire formats out of this shared contract.
