# M1 — Automated watchlist research

Status: implementation required. No commands below are advertised as available.

## Outcome

An operator selects sources, a watchlist, calendar and budgets. OpenQuant retains per-stock research and evaluates complete watchlist strategies with shared strategy cash and slots. It records evidence and continues without an open terminal. Follow S0–S5 in the [roadmap](../product/roadmap.md#m1-vertical-slices), starting with offline seed evaluation.

## Build and demonstrate

1. In S0 run the [daily swing seed](../specs/02-trading-domain-and-evaluation-spec.md#26-daily-swing-seed-family) as versioned Strategy Definitions through `packages/quant-core`'s reviewed typed operators. Encode threshold 30/32 and break-even off/on in the definitions; use one validator and evaluator. Add the Cargo workspace, pinned toolchain, lockfile and a small local harness with the working core. Add the input, numerical result and checkpoint schemas under `packages/api-contracts/schemas`, generate Rust bindings and validate shared payload fixtures. These are shared contracts, not temporary local formats. Verify the S0 cases in engineering §8 against independent calculations. Wire real Rust and schema checks into `scripts/verify.ts` and `.github/workflows/ci.yml`. Document the exact local command and expose signals, trades, cash, positions and input/engine identities. A Rust integration-test report is sufficient. Demonstrate schema-based state restore without duplicate split application. No provider credentials, model, cloud service, API service, TypeScript runtime or Ink view is required.
2. Deliver S1 through one complete one-stock mission: provider retrieval, immutable dataset, two proposer configurations, separate critique, registered evaluation, real Rust result, durable API read-back and a small Ink/JSON view. Reuse S0's verified core, toolchain, schemas and fixtures. Pass the seed and a proposer-authored controlled revision through the same Rust validator and evaluator. Show source interpretation changes and parent differences. Add strict TypeScript tooling, generated TypeScript bindings and validation against the shared fixtures. Add the connected run/attempt/ownership envelopes and verify that the boundary preserves S0's expected results and state. Register the pilot `strategy-formulation` and `strategy-critique` role modules from the `packages/agents` drafts with a bundle allowlist and offline suites, and no callable tools ([model execution §3](../specs/03-model-backed-execution-spec.md#3-delegated-execution-contract)). S0 must pass before S1 acceptance; provider setup and investigation may proceed in parallel.
3. In S2 add Massive behind the same market contract. Select the source in a versioned research profile. Demonstrate switching without workflow changes and an explicit [provider comparison](provider-comparison.md).
4. In S3 retrieve SEC filings and Tavily sources through bounded application tools. Store provenance, exclude evidence that violates the cutoff, and show partial retrieval. Evaluate citation fidelity and resistance to instructions embedded in source text. A current page is not proof of its historical contents. The first evidence tool adds the runner bridge, call records and a registered-tool probe ([engineering §8](../specs/06-engineering-delivery-and-operations-spec.md#8-delivery-checkpoints-and-acceptance)).
5. In S4 freeze watchlist membership and allocate budgets to both stock and joint work. Display every member's outcome. Use a bounded strategy-level mission over the same snapshot, then evaluate one policy with ranking, five slots and shared strategy cash through Rust. Run the [four-candidate comparison](../specs/02-trading-domain-and-evaluation-spec.md#37-controlled-seed-comparison) on common dates and inputs. Inspect joint results, contributions and skipped entries. Required missing data blocks joint evidence; other stock findings remain saved. Preserve old cycles when membership changes.
6. In S5 add stored schedule slots and bounded catch-up, pause/resume and explicit cancellation. Verify recovery without clients, shared provider/model/compute reservations and conservative unknown usage. Resume joint state including pending entries and scheduled stops. Supply later missions with permitted prior findings for bounded revisions; retain failed variants, lineage and holdout consumption.

## Acceptance handoff

Use [engineering §8](../specs/06-engineering-delivery-and-operations-spec.md#8-delivery-checkpoints-and-acceptance). Each slice records its implemented path, source revision, exact command, input/executable identities, independent expected results, actual results, adverse cases and remaining limits. S0 completes with its local result report and real Rust checks in `pnpm verify`. Record only the cases verified; local replay does not complete A03–A05 in full or establish A11 distributed recovery.

Slices that introduce or change external integrations also record the relevant live provider/executor probes and deployed identities. S1 requires real provider/model execution, basic durability, authority checks and deployment read-back. S2/S3 verify their added adapters; S5 verifies unattended operation and extended recovery. A recorded response cannot establish live service access.

The joint replay must demonstrate slot competition, input-order independence, common valuation dates, causal cash reuse, exact rounded-fill accounting and restart equivalence. Expected financial results come from independent calculations. This gate checks the complete policy inside one strategy; cross-strategy capital allocation remains M3.

M1 is complete only after all six outcomes and their applicable operating evidence exist. For S1 and later slices, a small UI is sufficient, but its commands still need authoritative read-back, explicit failure/pending states and the applicable A15 checks. No live orders are permitted. The [installed replay gate](public-cli-replay.md) remains required for public CLI release; S0 alone does not satisfy it.
