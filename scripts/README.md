# Repository tooling

The scripts use Node built-ins and erasable TypeScript syntax. Use `.node-version` (Node 24). The scripts directly under `scripts/` need no dependency install, so the repository checks run before anything is installed. The workspace checks in `scripts/workspace/` use installed dependencies (the `yaml` parser, Turborepo) and run only in the TypeScript steps of `verify.ts`, after the dependency check. The Rust steps need the toolchain pinned in `rust-toolchain.toml`.

| Script | Purpose |
| --- | --- |
| `verify.ts` | Run repository checks and their regression tests; the pinned-toolchain check, the Rust steps from `rust.ts`, the fixture-change guard and the S0 replay report check; then the dependency check, the TypeScript steps from `typescript.ts` and a second fixture-change guard. Fail on any failure. Every process it starts takes the environment from `environment.ts`. |
| `environment.ts` | `stepEnvironment()`: the caller's environment without the variables that change which tests run, how code is compiled or linked, which runner starts a test binary, which file a shell reads first, or how Turborepo runs (`NODE_OPTIONS`, `NODE_TEST_*`, `RUSTFLAGS`, `RUSTDOCFLAGS`, the Rust and Cargo wrapper and flag variables, `CARGO_TARGET_*_RUNNER`, `_RUSTFLAGS`, `_RUSTDOCFLAGS` and `_LINKER`, `BASH_ENV`, `ENV`, `TURBO_*`, `BIOME_CONFIG_PATH`), with `TURBO_TELEMETRY_DISABLED=1` and pnpm set to fail instead of installing. Proxy, certificate and toolchain variables are kept. |
| `rust.ts` | The Cargo commands run by `verify.ts` (format, clippy, tests, S0 replay, contracts report), the pinned-toolchain check and the fixture-change guard. |
| `typescript.ts` | The TypeScript commands run by `verify.ts` (the workspace checks, Turborepo `typecheck lint test build --force`, and the workspace tests, named one by one, with the reporter that fails a file that ran no test or a skipped test) and the dependency check: the running pnpm must be the `packageManager` version and `node_modules/.pnpm/lock.yaml` must equal `pnpm-lock.yaml` byte for byte. `pnpm-workspace.yaml` sets `verifyDepsBeforeRun: error` for `pnpm verify` and every other `pnpm run`, because pnpm 11 otherwise installs, and can rewrite `pnpm-lock.yaml`, before the script starts. |
| `s0.ts` | Static verification rules: Rust workspace and toolchain pin, tracked Cargo configuration and manifest settings that skip tests, the Cargo and TypeScript steps compared with literal expected lists, the reviewed code of `verify.ts`, `environment.ts`, `runCargo` and `runTypescript`, the environment of every process verification starts, the modules `verify.ts` imports, the workspace packages and their task scripts, files pinned by SHA-256, the TypeScript, Biome and Vitest settings that would let a check pass without checking, CI wiring, fixture case layout, oracle hashes, S0 row coverage, protocol manifest vocabulary and completeness; and the replay report check against the fixture inventory. |
| `check-repository.ts` | Check the seven specs, metadata/index, acceptance IDs, links/anchors, source hashes, file map, high-confidence credential patterns, private file names, and selected workflow conventions including the aggregate `ci` job. |
| `generate-spec-index.ts` | Generate the ownership/version table from document metadata. |
| `generate-repository-tree.ts` | Generate the sorted file map from the Git index, or regular files in an extracted archive. |
| `repository.ts` | Shared implementation, the ignored local-output names, the credential patterns and the text check of the aggregate job. |
| `development-skills.ts` | Check declared shared skills, aliases, installer records, adapted-file hashes, and complete portable resources with recorded hashes. |
| `agent-assets.ts` | Check the assets in `packages/agents`: exact layout including the five role schemas, source registry, method-note rule rows, rule references, finding-category parity with OQ-03 §4, the synthetic fixture policy, evaluation case fields and required case coverage. The link and blockquote rules read Markdown only. It does not check that a rule is true or that a procedure works. |
| `tests/repository.test.ts` | Negative cases for drift, missing requirements, links, provenance, credentials, mutable actions, archive path escape, agent asset rules and the verification rules; and behavioural tests of the `verify.ts` driver. |
| `workspace/check-workspace.ts` | Run the dependency-using checks: licences, import boundaries, workflows and Dependabot, and the Turborepo task list. |
| `workspace/licences.ts` | Licence allowlist over every installed npm package, derived from the locked dependency tree. A few licences are accepted only for named packages. |
| `workspace/boundaries.ts` | Import boundaries over source text: no `apps/api` import in `apps/cli` or `packages/api-client`; no Node built-in in Worker code (`packages/api-contracts/ts/src`, `apps/api/src`, `packages/agents/src`); no broker or `apps/engine` import in `apps/agent-runner`. |
| `workspace/tasks.ts` | Run `turbo run typecheck lint test build --dry=json` and require exactly the typecheck, lint, test and build task of every package in `expectedWorkspacePackages` (`s0.ts`), each with its pinned script and no extra arguments. |
| `workspace/test-reporter.ts` | The `node:test` reporter of the workspace tests: it fails a run in which a named file did not run, a file ran no test, or a test was skipped or marked todo. |
| `workspace/workflows.ts` | Parsed-YAML checks of the workflows and Dependabot: read-only permissions, no `continue-on-error`, no constant false `if`, pinned actions, unfiltered `pull_request` and `push` triggers; in `ci.yml`, the `checks` job with exactly the expected steps (names, action commits, `with` inputs, commands, no other key), its keys, runner and timeout, workflow and job `env` limited to `CARGO_INCREMENTAL: '0'` and `CARGO_TERM_COLOR: always`, no variable that could switch a step off anywhere, and an aggregate `ci` of a fixed shape that needs and checks every other job. |
| `workspace/tests/*.test.ts` | Tests of the workspace checks and of both reporters, including the eight CI edits of the S0 review (V2-1). The test step names each file; `workspaceTestFiles` in `s0.ts` lists them. |

In a Git checkout, stage intended added/deleted paths before generating the tree. The index records intended repository contents. An extracted ZIP has no `.git`, so the same tool reads its files and skips the ignored local output (`node_modules`, `target`, `dist`, `.turbo`, `.wrangler`, `coverage`, `.cache`, `local-runs`, `*.tsbuildinfo`).

Imported source Markdown is excluded from local-link checks because its historical links and layouts are intentionally unchanged. Every imported file remains covered by its SHA-256 check. Vendored skills and imported references are also excluded from the database-URL credential pattern, because their examples are bound by recorded hashes; every other credential pattern applies to them.

The workflow checks are static, not an Actions emulator or a full security audit. Type stripping does not type-check; the TypeScript steps run `tsc` on the workspace packages, not on these scripts. S0 added Rust verification. S1 adds the TypeScript steps; the connected competition, real-Postgres tests and application tests arrive with the rest of S1. Public CLI release adds installed-package validation.

## How verification is guarded

The guards do not read their expectation from the file they check. A change to a guarded file is therefore a change to `s0.ts` or `workspace/workflows.ts` in the same review.

- `expectedCargoCommands` and `expectedTypescriptCommands` in `s0.ts` are literal ordered lists. `s0Errors` compares the real `cargoCommands` from `rust.ts` and `typescriptCommands` from `typescript.ts` with them by exact equality, so a dropped step, a changed flag (`--locked`, `-D warnings`, `--force`), an added `--lib` or `--no-run`, an added install, a glob in place of the named workspace test files, a duplicate or a reordering fails.
- `verify.ts` and `environment.ts` must equal their reviewed code in `s0.ts` (`expectedVerifyCode`, `expectedEnvironmentCode`), and `runCargo` and `runTypescript` must equal `expectedRunCargoCode` and `expectedRunTypescriptCode`. The comparison reads the code without comments, trailing spaces and blank lines, so comments may change and any statement added anywhere, such as an early `process.exit` or an assignment to `process.env`, fails. `verifyDriverErrors`, `rustModuleErrors`, `typescriptModuleErrors` and `environmentModuleErrors` also keep their shape checks, which say which binding statement is missing: the exit-code check on every step, each fixture digest taken before and compared after, the toolchain pin check, the `reportErrors` call, the dependency check before the TypeScript steps, the byte comparison of the installed and committed lockfiles, the pnpm version check and the step environment. `withoutComments` is not a parser; it only has to read these files.
- Every `spawnSync` call in the verification scripts (`scripts/*.ts` and `scripts/workspace/*.ts`, not the tests or the guard `s0.ts`) passes `env: stepEnvironment()` as its last option, and `spawnSync` is the only `node:child_process` import. The modules that `verify.ts` imports (`repository.ts`, `rust.ts`, `typescript.ts`, `development-skills.ts`, `agent-assets.ts`) may not use `process`, `globalThis`, `eval`, `Function`, `Reflect`, prototypes, `require` or a dynamic import, and may not reassign a function they declare, because their top-level code runs before step 1. `repository.ts` must set `root` to the directory above `scripts/`.
- The driver tests run the real `verify.ts`, `environment.ts`, `rust.ts`, `typescript.ts` and `s0.ts` in a temporary root. The other inputs are stand-ins: `scripts/check-repository.ts` and `scripts/tests/repository.test.ts` in that root (the driver would otherwise run this test file again and recurse), a lockfile and its installed copy, and `cargo`, `rustc` and `pnpm`, shell scripts placed first on `PATH`. The stand-ins record their arguments in one log, can exit non-zero for a chosen step, can change a fixture, and can write a replay report; the `pnpm` stand-in answers the version check and refuses a step without the environment the driver must set, and every stand-in refuses to run when a variable that `stepEnvironment()` removes reaches it. One test starts the driver with every such variable set and expects every step to run; another lets one variable through in a copied script and expects the run to fail. The tests need `sh` and are skipped on Windows. They take a few seconds each.
- `expectedWorkspacePackages` in `s0.ts` lists the workspace packages and the exact `typecheck`, `lint`, `test` and `build` script of each. `pnpm-workspace.yaml` must list exactly those packages, one per line, and each `package.json` must hold exactly those scripts. Before Turborepo runs, `workspace/tasks.ts` compares its dry run with the same list, so a workspace without a package, a package without a task, another script or extra arguments fails instead of a run of zero tasks that passes.
- A test run must execute tests. The package `test` script names `test-reporter.ts`, a Vitest reporter that fails a run in which a test module ran no test or a test was skipped, marked todo or filtered out by a name pattern; Vitest alone passes such a run. The workspace tests use `workspace/test-reporter.ts` in the same way for `node:test`. Both reporters and each package's `vitest.config.ts` are pinned by SHA-256 in `pinnedFiles`. `s0Errors` also rejects `noCheck` or `strict: false` in a `tsconfig*.json`, a Biome linter that is not `{"enabled": true, "rules": {"preset": "recommended"}}`, Biome overrides or a nested Biome configuration, `testNamePattern`, `allowOnly` or a `passWithNoTests` other than `false` in a Vitest configuration, `@ts-nocheck` or `biome-ignore-all` in package sources, and `.skip`, `.only`, `.todo`, `.skipIf` or `.runIf` in package test sources.
- A tracked `.cargo/config` or `.cargo/config.toml` anywhere in the repository fails, because Cargo reads it from the directory it runs in and every parent (rustflags such as `--cap-lints`, a test runner, a wrapper or an alias). So does `autotests`, `autobins`, `test`, `harness` or `doctest` set to `false` in any tracked `Cargo.toml`.
- `reportErrors` lists the directories under `fixtures/s0/cases`. The replay index and the report must hold exactly those case ids, each once, and the `- cases: N` line must equal their number. A replay of part of the inventory fails even when every listed case passed.
- Every entry of `fixtures/protocol/manifest.json` must use an `expect` of `valid`, `schema_invalid` or `semantic_invalid` and one of the engine or connected contract names, because the Rust tests select entries by those values and silently skip any other. Every file must be listed and every listed file must exist.
- The CI checks run twice. `s0.ts` and `repository.ts` check the text without dependencies. `workspace/workflows.ts` parses the YAML: the `checks` job must hold exactly the expected steps, so `|| true`, an `echo`, a constant false `if`, a commented or extra step, `env` on a step (such as `BASH_ENV`), a checkout of another `ref`, `repository` or `path`, another action commit, a container or another runner, and a removed trigger fail (S0 review finding V2-1 and P1 review finding C0). A Dependabot update of `actions/checkout` or `actions/setup-node` changes `expectedChecksSteps` in the same review.

Expected values in `fixtures/s0/cases/*/expected.json` are bound to `origin.oracle_sha256` and to CODEOWNERS review of `/fixtures/`; `verify` does not re-derive them, because OQ-06 section 8 requires no second numerical engine in verification, so a golden change is a reviewed change with an explained semantic reason and never a side effect of a test run.
