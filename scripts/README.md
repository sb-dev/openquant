# Repository tooling

The scripts use Node built-ins and erasable TypeScript syntax. Use `.node-version` (Node 24). The scripts directly under `scripts/` need no dependency install, so the repository checks run before anything is installed. The workspace checks in `scripts/workspace/` use installed dependencies (the `yaml` parser) and run only in the TypeScript steps of `verify.ts`, after the dependency check. The Rust steps need the toolchain pinned in `rust-toolchain.toml`.

| Script | Purpose |
| --- | --- |
| `verify.ts` | Run repository checks and their regression tests; the pinned-toolchain check, the Rust steps from `rust.ts`, the fixture-change guard and the S0 replay report check; then the dependency check, the TypeScript steps from `typescript.ts` and a second fixture-change guard. Fail on any failure. |
| `rust.ts` | The Cargo commands run by `verify.ts` (format, clippy, tests, S0 replay, contracts report), the pinned-toolchain check and the fixture-change guard. |
| `typescript.ts` | The TypeScript commands run by `verify.ts` (Turborepo `typecheck lint test build --force`, the workspace checks and their tests) and the dependency check: the running pnpm must be the `packageManager` version and `node_modules/.pnpm/lock.yaml` must equal `pnpm-lock.yaml` byte for byte. Each step runs with `TURBO_TELEMETRY_DISABLED=1` and with pnpm set to fail instead of installing when it finds the install out of date. `pnpm-workspace.yaml` sets the same for `pnpm verify` and every other `pnpm run` (`verifyDepsBeforeRun: error`), because pnpm 11 otherwise installs, and can rewrite `pnpm-lock.yaml`, before the script starts. |
| `s0.ts` | Static verification rules: Rust workspace and toolchain pin, the Cargo and TypeScript steps compared with literal expected lists, the code shapes `verify.ts`, `rust.ts` and `typescript.ts` must keep, CI wiring, fixture case layout, oracle hashes, S0 row coverage, protocol manifest vocabulary and completeness; and the replay report check against the fixture inventory. |
| `check-repository.ts` | Check the seven specs, metadata/index, acceptance IDs, links/anchors, source hashes, file map, high-confidence credential patterns, private file names, and selected workflow conventions including the aggregate `ci` job. |
| `generate-spec-index.ts` | Generate the ownership/version table from document metadata. |
| `generate-repository-tree.ts` | Generate the sorted file map from the Git index, or regular files in an extracted archive. |
| `repository.ts` | Shared implementation, the ignored local-output names, the credential patterns and the text check of the aggregate job. |
| `development-skills.ts` | Check declared shared skills, aliases, installer records, adapted-file hashes, and complete portable resources with recorded hashes. |
| `agent-assets.ts` | Check the assets in `packages/agents`: exact layout including the five role schemas, source registry, method-note rule rows, rule references, finding-category parity with OQ-03 §4, the synthetic fixture policy, evaluation case fields and required case coverage. The link and blockquote rules read Markdown only. It does not check that a rule is true or that a procedure works. |
| `tests/repository.test.ts` | Negative cases for drift, missing requirements, links, provenance, credentials, mutable actions, archive path escape, agent asset rules and the verification rules; and behavioural tests of the `verify.ts` driver. |
| `workspace/check-workspace.ts` | Run the dependency-using checks: licences, import boundaries, workflows and Dependabot. |
| `workspace/licences.ts` | Licence allowlist over every installed npm package, derived from the locked dependency tree. A few licences are accepted only for named packages. |
| `workspace/boundaries.ts` | Import boundaries over source text: no `apps/api` import in `apps/cli` or `packages/api-client`; no Node built-in in Worker code (`packages/api-contracts/ts/src`, `apps/api/src`, `packages/agents/src`); no broker or `apps/engine` import in `apps/agent-runner`. |
| `workspace/workflows.ts` | Parsed-YAML checks of the workflows and Dependabot: read-only permissions, no `continue-on-error`, no constant false `if`, pinned actions, unfiltered `pull_request` and `push` triggers, the exact install and verify steps in order, the `checks` timeout, and an aggregate `ci` that needs and checks every other job. |
| `workspace/tests/*.test.ts` | Tests of the workspace checks, including the eight CI edits of the S0 review (V2-1). |

In a Git checkout, stage intended added/deleted paths before generating the tree. The index records intended repository contents. An extracted ZIP has no `.git`, so the same tool reads its files and skips the ignored local output (`node_modules`, `target`, `dist`, `.turbo`, `.wrangler`, `coverage`, `.cache`, `local-runs`, `*.tsbuildinfo`).

Imported source Markdown is excluded from local-link checks because its historical links and layouts are intentionally unchanged. Every imported file remains covered by its SHA-256 check. Vendored skills and imported references are also excluded from the database-URL credential pattern, because their examples are bound by recorded hashes; every other credential pattern applies to them.

The workflow checks are static, not an Actions emulator or a full security audit. Type stripping does not type-check; the TypeScript steps run `tsc` on the workspace packages, not on these scripts. S0 added Rust verification. S1 adds the TypeScript steps; the connected competition, real-Postgres tests and application tests arrive with the rest of S1. Public CLI release adds installed-package validation.

## How verification is guarded

The guards do not read their expectation from the file they check.

- `expectedCargoCommands` and `expectedTypescriptCommands` in `s0.ts` are literal ordered lists. `s0Errors` compares the real `cargoCommands` from `rust.ts` and `typescriptCommands` from `typescript.ts` with them by exact equality, so a dropped step, a changed flag (`--locked`, `-D warnings`, `--force`), an added `--lib` or `--no-run`, an added install, a duplicate or a reordering fails. A change to a step is therefore a change to two files in one review.
- `verifyDriverErrors`, `rustModuleErrors` and `typescriptModuleErrors` require code shapes, not identifiers: the exit-code check on every Cargo and TypeScript step, each fixture digest taken before and compared after, the toolchain pin check, the `reportErrors` call, the dependency check before the TypeScript steps, `runCargo` and `runTypescript` returning the exit status, the step environment, the byte comparison of the installed and committed lockfiles, and the pnpm version check. They read the source without comments, so a comment cannot satisfy them, and they check the order. `withoutComments` is not a parser; it only has to read these files.
- The driver tests run the real `verify.ts`, `rust.ts`, `typescript.ts` and `s0.ts` in a temporary root. The other inputs are stand-ins: `scripts/check-repository.ts` and `scripts/tests/repository.test.ts` in that root (the driver would otherwise run this test file again and recurse), a lockfile and its installed copy, and `cargo`, `rustc` and `pnpm`, shell scripts placed first on `PATH`. The stand-ins record their arguments in one log, can exit non-zero for a chosen step, can change a fixture, and can write a replay report; the `pnpm` stand-in answers the version check and refuses a step without the environment the driver must set. There is no switch in `verify.ts`, so nothing in a normal run can disable a step. The tests need `sh` and are skipped on Windows. They take a few seconds each.
- `reportErrors` lists the directories under `fixtures/s0/cases`. The replay index and the report must hold exactly those case ids, each once, and the `- cases: N` line must equal their number. A replay of part of the inventory fails even when every listed case passed.
- Every entry of `fixtures/protocol/manifest.json` must use an `expect` of `valid`, `schema_invalid` or `semantic_invalid` and one of the engine or connected contract names, because the Rust tests select entries by those values and silently skip any other. Every file must be listed and every listed file must exist.
- The CI checks run twice. `s0.ts` and `repository.ts` check the text without dependencies. `workspace/workflows.ts` parses the YAML, so `|| true`, an `echo`, a constant false `if`, a commented step or timeout, and a removed trigger fail (S0 review finding V2-1).

Expected values in `fixtures/s0/cases/*/expected.json` are bound to `origin.oracle_sha256` and to CODEOWNERS review of `/fixtures/`; `verify` does not re-derive them, because OQ-06 section 8 requires no second numerical engine in verification, so a golden change is a reviewed change with an explained semantic reason and never a side effect of a test run.
